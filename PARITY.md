# Original Mode A comparison and acceptance boundary

Source: [upstream README](https://github.com/frankee0920-rgb/rhino-architectural-reverse-modeling), [upstream SKILL.md](https://github.com/frankee0920-rgb/rhino-architectural-reverse-modeling/blob/main/rhino-architectural-reverse-modeling-mode-a/SKILL.md). The original repository is an agent skill and does not bundle Rhino or its MCP server. This project is a separate license-independent implementation, not Rhino or a license bypass. The new MCP can now save a validated component spec from a natural-language agent call; this removes the need for direct host filesystem write access to its workspace.

| User-facing contract | Original Mode A | Current license-independent implementation | Status |
|---|---|---|---|
| Install skill in host project | Copy skill folder to `.agents/skills` or `.claude/skills` | `scripts/install_skill.py` copies the self-contained `skill/sodam-rhino-architectural-modeling` folder and checks MCP; existing conflicting entries are preserved | Same folder method; extra local runtime needed |
| Ask with photos, description, dimensions | Agent interprets references and chooses modeling actions | New skill directs agent to build a component JSON; evidence packet records photos, dimensions, and assumptions | Similar request flow; no autonomous photogrammetry |
| Create arbitrary detailed building geometry | Rhino MCP can operate Rhino's modeling engine | JSON supports four kinds (box, wall_opening, gable_roof, cylinder); Blender source scenes can supply other evaluated mesh forms via `import_blender_scene` | Mesh geometry broader; Rhino operations not equivalent |
| Revise the model | Rhino document objects can be edited through Rhino | `revise_architectural_spec` replaces one named JSON component in a new spec; rebuild a new `.3dm`, or edit source `.blend` and import it back | JSON revision and Blender 4.5 scene editing/import tested; direct `.3dm` editing absent |
| Editable native deliverable | `.3dm` by default, `.blend` when the user chooses an alternative | `.3dm` meshes with layers, names, and control JSON; optional `.blend` scene from saved model | File formats match; Rhino NURBS/Boolean editing does not |
| Materials and actual model renders | Materials, saved views, main and complementary rendered images | Basic RGB materials, two adjustable Blender camera views and saved `.blend`; fallback orthographic inspection PNGs | Basic output only; camera/material matching unproved |
| Verification | Reopen model, check form/scale/assembly/details and compare views to references | Reopen `.3dm`, inspect geometry metadata, render and inspect actual output; provenance checks distinguish known and inferred values | Technical pipeline proved on synthetic cases; real-photo accuracy not proved |

## Required proof before claiming original-level use

1. Start a new Codex/Claude session in the installed project, invoke the skill through natural language, and observe its MCP calls. File placement and command-line MCP tests alone do not prove host skill selection.
2. For each representative real request, compare building silhouette, measured dimensions, openings, levels, assembly, materials, and camera alignment against source evidence. Use a separate reference file set; current synthetic cases are not a substitute.
3. Open the delivered `.3dm` in a compatible independent application and exercise the edits the user actually needs. The current `rhino3dm` round trip does not prove Rhino-native editability.
4. Classify unsupported shapes and Rhino-specific operations as gaps. [McNeel states](https://developer.rhino3d.com/guides/opennurbs/what-is-opennurbs/) that openNURBS does not supply intersections, meshing, Booleans, and other full Rhino geometry operations; a `.3dm` writer alone cannot close this gap.

Current verified operations: project skill copy and repeat-install check, Codex MCP registration at the requested path, twelve MCP tools available over stdio, including validated spec saving, Blender .blend to 3DM import and reopen, `.3dm` build/reopen, two actual Blender renders, saved `.blend` reopening, and the current unit test suite. These prove the supported pipeline, not exact Rhino operation or real-photo accuracy.


`rhino3dm` 8.35.0 named-view probing did not produce a valid viewport: `SetScreenPort` left port extents at zero. No named Rhino view is claimed in the `.3dm`; the two tested Blender cameras remain in the `.blend`.

## Adjustable Blender view acceptance — 2026-09-24

The original workflow requires a main and complementary view. Previously, Blender always rendered 315°/28° and 135°/28°, so an agent could not aim its main view at a reference. `render_blender_model`, the CLI, and the saved `.blend` now accept front/rear azimuth and elevation while retaining those defaults. Finite numeric angles and elevation bounds are validated before Blender starts; views separated by less than 10° (including polar cases with different azimuths) are rejected. No automatic photo registration is claimed.

After the change, all 32 unit tests, `compileall`, and Ruff E4/E7/E9/F passed. A second real Blender run comparing default and custom angles found different front image pixels; the custom saved blend was nonempty. The model is still a simple synthetic house, so this proves camera control and output generation, not photograph matching.

Full Ruff still reports 11 convention/style findings. Full mypy still fails mainly where rhino3dm 8.35.0 type metadata disagrees with exercised runtime behavior.
